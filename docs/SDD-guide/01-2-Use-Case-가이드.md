# Use Case 작성·검토 가이드

[전체 흐름](./00-SDD-전체-흐름.md)에서 1차 Phase II에 해당한다. 이 문서는 Use Case의 작성 단위, 항목, 작성·검토 순서와 예시를 다룬다. 단계와 문서 간 연결은 전체 흐름에서 확인한다.

## 1. 무엇을 만드는가

Use Case는 **사용자 또는 외부 시스템이 하나의 목표를 이루기 위해 우리 시스템과 주고받는 행동·결과**를 설명한다. 예를 들어 ‘예약하기’는 목표가 될 수 있지만 ‘저장 버튼 클릭’은 그 안의 행동이고, ‘예약 관리’는 여러 목표를 묶은 범위일 수 있다. 단위는 문서 이름보다 사용자가 끝냈다고 인식하는 결과로 판단한다.

## 2. 먼저 쓰고 다듬는 순서

1. PRD에서 이번 범위의 사용자 목표를 찾아 Use Case 목록을 만든다. PRD에 [핵심 사용 흐름](./01-1-PRD-가이드.md#핵심-사용-흐름)이 있으면 그 단계와 인계를 출발점으로 삼고, 흐름의 단계와 Use Case가 서로를 찾을 수 있게 연결한다. 흐름의 한 단계가 꼭 Use Case 하나가 되는 것은 아니다. 각 항목에 알아볼 수 있는 이름과 참조 가능한 식별자를 붙인다. 처음부터 모든 항목을 같은 깊이로 쓰지 않는다.
2. 대표 목표 하나의 성공 흐름을 쉬운 문장으로 쓴다. 누가 무엇을 하면 시스템이 무엇을 보여주거나 처리하는지, 목표에 도달할 때까지 연결한다.
3. 시작 전에 이미 갖춰져야 할 상태와 실제 시작 사건을 구분한다. 흐름 도중 판단할 조건을 사전 조건에 넣어 예외를 숨기지 않는다.
4. 성공 후 결과와, 중요한 실패에도 유지할 결과를 정한다. 각 단계에서 실제로 필요한 선택·실패·취소가 있으면 어느 단계에서 갈라지고 어디로 돌아가거나 끝나는지 적는다.
5. 적용할 업무 규칙과 PRD 근거를 연결한다. 기존 규칙을 복제하지 않는다. AI가 제안한 정책·기본값은 사람의 결정 전까지 제안으로 표시한다.
6. Design에서 같은 흐름을 따라가며 정보·행동·결과가 보이는지 확인한다. 화면에서 발견한 빠진 규칙은 요구에, 표현 문제는 Design에 반영한다. 이번 범위의 다른 주요 목표로 검토를 넓힌다.

사람은 익숙한 업무 말로 초안을 써도 된다. AI가 아래 항목으로 정리하고 누락을 제안할 수 있지만 업무 정책을 대신 확정하지 않는다. 기술 구현은 2차 Spec에서 정한다.

## 3. 항목별 의미

**작성 여부**는 [PRD 가이드의 구분](./01-1-PRD-가이드.md#2-prd에-담을-내용)을 따른다. 행위자·목표, 시작 사건, 기본 성공 흐름, 성공 후 조건은 **필수**다. 사전 조건·대체 흐름·실패 시 보장·업무 규칙은 해당하는 상황이나 규칙이 있을 때 적는 **해당 시 필수**다.

| 항목 | 적을 내용 | 작성 여부 |
|---|---|---|
| 행위자·목표 | 누가 어떤 일을 끝내려는지 | 필수 |
| 시작 사건 — Trigger | 어떤 요청·시점·외부 사건으로 시작하는지 | 필수 |
| 사전 조건 — Preconditions | 시작 전에 이미 성립해 있어야 하는 상태 | 해당 시 필수 |
| 기본 성공 흐름 — Main Success Scenario | 정상적으로 목표에 도달하는 행동과 시스템의 반응. 순서대로 번호를 붙인다. | 필수 |
| 대체·예외 흐름 — Alternative Flows | 어느 단계에서 어떤 조건으로 달라지고, 그 뒤 어떻게 이어지거나 끝나는지. 성공하는 다른 선택도 포함할 수 있다. | 해당 시 필수 |
| 성공 후 조건 — Success Postconditions | 성공 후 남는 상태·산출물·처리 결과. 안내 메시지만으로 결과를 설명하지 않는다. | 필수 |
| 실패 시 보장 — Failure Postconditions | 목표를 이루지 못해도 보호해야 할 정보나 상태 | 해당 시 필수 |
| 업무 규칙 — Business Rules | 적용되는 허용·금지·계산·판정 기준. 공통 원문을 참조하고 이 흐름만의 차이를 적는다. | 해당 시 필수 |

**작성할 때:**

- 목표는 사용자가 끝내려는 일로 정한다. 화면 이름이나 내부 기술 처리만으로 정하지 않으며, 흐름에 API 경로·SQL·클래스 구조를 넣지 않는다.
- 시작 사건과 사전 조건을 구분한다. ‘로그인돼 있다’는 상태이고 ‘예약을 요청한다’는 사건이다. 흐름 도중 확인할 ‘선택한 시간이 비어 있다’ 같은 조건을 미리 참이라고 두지 않는다.
- 실패 대응과 실패 시 보장을 구분한다. ‘오류 메시지를 띄운다’는 대응이고 ‘기존 기록은 훼손되지 않는다’는 보장이다.

관련 요구 위치와 작성·검토 상태도 남긴다. 특별한 사전 조건이나 의미 있는 대체 흐름이 없으면 **해당 없음**으로 밝힌다. 필요한 내용의 답을 아직 모르면 **미결**로 남기고 관련 설계·구현 전에 해결한다. 양식을 채우려고 존재하지 않는 조건이나 예외를 만들지 않는다. Use Case가 여러 개인 경우 꼭 파일을 하나씩 만들 필요는 없지만 독립적으로 참조할 수 있어야 한다.

## 4. 작성 예시 — 방문 시간 예약

아래는 작성법을 설명하기 위한 가상 정책이다. 현재 제품의 확정 요구가 아니다.

- **행위자·목표:** 고객이 방문 시간을 예약하고 확정 여부를 확인한다.
- **시작 사건:** 고객이 새 예약을 요청한다.
- **사전 조건:** 매장의 예약 서비스와 운영 일정이 등록돼 있다.
- **기본 성공 흐름:** ① 고객이 날짜를 지정한다 → ② 시스템이 선택 가능한 시간을 보여준다 → ③ 고객이 시간을 선택하고 필요한 정보를 입력한다 → ④ 시스템이 입력과 현재 예약 가능 여부를 확인한다 → ⑤ 고객이 예약을 확정한다 → ⑥ 시스템이 최종 가능 여부를 확인해 예약을 기록하고 결과를 알려준다.
- **대체 흐름 A1:** ②에서 선택 가능한 시간이 없으면 고객에게 알리고 ①로 돌아가거나 종료한다.
- **대체 흐름 A2:** ⑥에서 다른 예약으로 시간이 이미 찼으면 예약을 만들지 않고, 최신 선택지로 ②부터 다시 진행하도록 안내한다.
- **성공 후 조건:** 고객이 선택한 시간의 예약이 확정 상태로 저장되고, 같은 시간은 새 예약에 제공되지 않는다.
- **실패 시 보장:** 이 예시에서 ‘실패로 종료’한 경우 새 확정 예약이 생기지 않고 기존 예약은 변경되지 않는다.
- **업무 규칙:** 이 예시에서는 시간대당 한 건만 확정한다. 실제 제품에서는 다중 예약 허용 여부를 별도로 결정한다.

‘선택한 시간이 비어 있음’을 사전 조건으로 쓰면 ⑥의 경합 상황을 놓치기 쉽다. 또한 저장됐지만 결과 전달이 끊긴 상황은 확정 실패와 같지 않다. 그런 상황이 중요한 제품이라면 처리 결과 확인·재시도·중복 방지 흐름을 별도로 정해야 한다. 위 예시만으로 모든 실패가 명세됐다고 보지 않는다.
