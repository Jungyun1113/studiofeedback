# PRD 작성·검토 가이드

[전체 흐름](./00-SDD-전체-흐름.md)에서 1차 Phase I에 해당한다. 이 문서는 PRD의 내용과 작성·검토 방법을 다룬다. 단계와 문서 간 연결은 전체 흐름에서 확인한다.

## 1. 무엇을 만드는가

**제품 PRD 하나로 시작한다.** 기존 메모나 PRD가 있다면 재사용한다. 목표는 다음 설계에 필요한 제품 결정을 사람이 이해하고 정리하는 것이다.

PRD는 **누가 제품으로 무엇을 하며, 어떤 조건에서 어떤 결과가 생겨야 하는지** 정리한 문서다. 필요한 제품 결정을 적고 아직 정하지 못한 것은 미결로 남긴다.

제품의 방향과 요구를 스스로 생각하고 작성·검토한다. AI 인터뷰는 누락·충돌이나 막힌 결정을 보완하는 수단으로 사용한다.

## 2. PRD에 담을 내용

다음 다섯 관점으로 PRD에 필요한 내용이 있는지 확인한다. 고정 목차로 따라 쓸 필요는 없으며, 같은 내용이 기능 설명이나 흐름에 이미 있으면 반복하지 않는다.

표의 **작성 여부**는 그 내용을 PRD에 얼마나 반드시 담아야 하는지를 뜻한다. 이 가이드의 안내 표시이므로, 실제 PRD에 항목마다 표시를 붙일 필요는 없다.

| 작성 여부 | 어떻게 적용하나 | 예시 |
|---|---|---|
| **필수** | 모든 제품에서 정하고 적는다. | 누가 사용하는지, 이번에 무엇을 만드는지 |
| **해당 시 필수** | 설명된 상황이 있으면 반드시 정하고 적는다. 해당하지 않으면 생략한다. | 다른 사람에게 일이 넘어간다면 인계 시점과 다음 담당자의 일 |
| **권장** | 이해와 판단에 도움이 되어 작성을 추천한다. 없어도 PRD의 결함으로 보지 않는다. | 핵심 사용 흐름, 기대 변화 |
| **선택** | 기본 작성 항목에 더해, 해당 제품을 설명하는 데 필요할 때 작성한다. | 장기 방향, 지향하지 않는 방향 |

**미결은 작성 여부와 별개다.** 필요한 내용의 답을 아직 모르면 질문과 결정 시점을 남기고, 그 결정에 의존하는 설계·구현 전에 해결한다. ‘해당하지 않음’과 ‘아직 모름’을 구분한다.

작성 방법과 검토할 질문은 표 아래에 따로 설명한다. 이를 위해 별도 문단·목록이나 새 기능을 추가할 필요는 없다.

### ① 제품의 방향

| 항목 | 적을 내용 | 작성 여부 |
|---|---|---|
| 대상 사용자(Target User) | 누가 사용하는가. 상세 페르소나·시장 분석은 요구하지 않는다. | 필수 |
| 제품이 해결하고자 하는 문제·사용자가 하려는 일 | 해결할 문제나 제품으로 하려는 일을 적는다. 둘 다 따로 작성하거나 기존 불편을 증명할 의무는 없다. 대상 사용자와 구분한다. | 필수 |
| 확인된 불편과 새로운 대안 | 알고 있는 현재의 불편과 다른 방법을 적을 수 있다. 조사나 기존 불편의 증명을 시작 조건으로 삼지 않는다. | 권장 |
| 기대 변화 | 제품 사용 후 바라는 변화를 적을 수 있다. 별도 설명이나 수치 목표가 없어도 결함은 아니다. | 권장 |
| 장기 방향 | 이번 범위 밖의 지속적인 방향이 판단에 도움이 될 때 적는다. | 선택 |
| 지향하지 않는 방향 | 제품 경계를 설명할 필요가 있을 때 적는다. | 선택 |

**작성할 때:** 근거로 제시하는 사실, 아직 확인하지 않은 가설, 제품 결정을 구분한다. 별도 가설 목록이나 검증 계획을 만들 필요는 없다.

예: 고객은 헤어샵 방문 시간을 예약하고, 매장은 예약 현황을 확인한다. 현재 예약 방식의 불편을 알고 있다면 근거로 덧붙일 수 있다.

### ② 이번에 만들 범위(Scope)

| 항목 | 적을 내용 | 작성 여부 |
|---|---|---|
| 포함 범위(In Scope) | 이번에 제공할 업무·기능을 명시한다. 다른 설명에서 분명하다면 반복하지 않는다. | 필수 |
| 제외 범위(Out of Scope) | 구상에는 있지만 이번에 제외하거나, 포함으로 오해할 만한 것을 명시한다. | 해당 시 필수 |
| 미정 범위 | 이번 포함 여부가 미결인 것을 명시한다. 떠올릴 수 있는 기능을 모두 나열하지 않는다. | 해당 시 필수 |
| 반드시 필요한 것·조정 가능한 것 | 범위 조정에 도움이 될 때 구분한다. 모든 기능에 등급을 매기지 않으며, 미분류를 제외 가능으로 취급하지 않는다. | 권장 |
| 외부 처리 | 목적 달성에 필요한 외부 처리가 있으면 그 사실을 명시한다. 세부 운영 절차는 운영 시작 때 정할 수 있지만, 제품 입력·행동·결과를 바꾸는 조건은 관련 설계 전에 정한다. | 해당 시 필수 |
| 예산·기한·외부 제약 | 이미 정해졌고 이번 제품에 영향을 주는 조건만 적는다. 임의로 만들지 않고 희망 조건과 구분한다. | 해당 시 필수 |

**확인할 것:** 이번 범위와 필요한 외부 처리를 연결했을 때, 사용자가 하려는 일을 마칠 수 있는가? 이 질문에 대한 답을 별도 문단으로 반복할 필요는 없다.

필요한 기능인지, 이번 범위인지, 언제 상세히 결정할지를 구분한다. ‘나중에 검토’를 개발 확정 약속으로 쓰지 않는다. 제품이 지향하지 않는 방향과 이번 버전의 제외 범위도 다르다.

### ③ 사용자 목적에 연결된 기능의 동작과 규칙

먼저 **누가 어떤 목적을 이루려고 이 기능을 쓰는지** 확인한다. 예를 들어 고객은 방문 시간을 예약하려 하고, 매장은 예약 현황을 확인하려 한다. User Story는 이 연결을 살피는 방법이며, 별도 목록을 만들 필요는 없다.

기능별 설명 앞에는 **핵심 사용 흐름**을 두기를 권장한다. 역할별 **목적 → 핵심 행동 → 결과**를 짧게 이어 이번 범위의 일이 어떻게 연결되는지 보여준다. 여러 사용자의 일은 역할별로 나누고, 일이 다른 사람에게 넘어가는 지점을 표시한다. 작성 방법과 예시는 아래 [핵심 사용 흐름](#핵심-사용-흐름)을 참고한다.

#### 기능별 동작과 규칙

각 기능은 다음 다섯 질문에 답하는 방식으로 적는다. **앞의 세 질문은 필수**, 뒤의 두 질문은 **해당 시 필수**다. 조건이나 예외가 있다면 허용 여부와 결과를 적고, 답을 아직 정하지 못했다면 미결로 남긴다.

| 묻는 것 | 적을 내용 | 작성 여부 |
|---|---|---|
| **무엇을 할 수 있나** | 만들기 · 보기 · 바꾸기 · 지우기 등 제공하는 행동 | 필수 |
| **누가 할 수 있나** | 그 행동을 누가 할 수 있는지. 저장한 정보는 누가 보고, 누가 바꾸는지 | 필수 |
| **하고 나면** | 무엇이 남고, 무엇이 바뀌는지. 조회라면 어떤 정보를 받는지 | 필수 |
| **언제만 되나** | 조건 · 상태에 따라 허용되거나 막히는 경우 | 해당 시 필수 |
| **안 되면** | 실패 · 예외일 때 처리와 결과 | 해당 시 필수 |

행동은 ‘예약하기’, ‘신청 승인하기’처럼 사용자가 하려는 일의 이름으로 적어도 된다. 만들기·보기·바꾸기·지우기를 모두 제공할 의무는 없다. 화면 연결과 조작 경로는 UX에서 구체화하며, 모든 클릭을 별도 기능으로 나누지 않는다.

다음은 ‘예약하기’를 설명하는 가상 예시이며, 헤어샵 예약 앱의 확정 요구가 아니다.

> 고객은 방문 시간을 선택해 예약할 수 있다. 고객은 본인의 예약을, 매장 직원은 소속 매장의 예약을 볼 수 있다. 예약이 완료되면 예약 내역이 남고 해당 시간은 다른 고객이 예약할 수 없게 된다. 이미 예약된 시간에는 예약할 수 없다. 저장에 실패하면 예약은 완료되지 않으며, 완료된 것으로 표시하지 않는다.

#### 해당할 때 더 적거나 확인할 내용

- **필요한 정보와 입력:** 행동에 필요한 정보가 준비될 수 있는지 확인한다. 입력이 있다면 무엇을 반드시 입력하고 무엇을 생략할 수 있는지 적는다. 직접 등록·가져오기 등이 필요하면 범위와 기능에 반영하고, 준비 방법을 모르면 미결로 남긴다. 글자 수는 업무상 의미가 있을 때만 정한다.
- **역할과 인계:** 역할·소유자·소속에 따라 맡는 일이나 권한이 다르면 구분한다. 일이 다른 사람에게 넘어가면 언제 넘어가고 다음 사람이 무엇을 하는지 적는다. 알림 수단은 필요에 따라 UX에서 정한다.
- **조건과 상태:** 시작 전에 필요한 조건이나 상태별로 달라지는 행동을 ‘언제만 되나’에 적는다. 상태를 사용한다면 그 의미도 설명한다. 취소·반려·재시도가 업무 결과에 영향을 주면 허용 여부와 처리 후 결과를 적는다. ‘취소 불가’도 결정이다.
- **실패와 금지 결과:** 업무나 남는 정보에 영향을 주는 실패·예외를 ‘안 되면’에 적는다. 권한 없는 기록 변경이나 실패한 저장의 성공 표시처럼 일어나면 안 되는 결과도 명시한다. 버튼을 숨긴다는 설명만으로 권한 규칙을 대신하지 않는다. 모든 기술 오류나 안내 문구를 나열할 필요는 없다.

같은 규칙은 적용 범위를 밝히고 한 번 적는다. 기능별 설명에는 다른 조건만 덧붙인다. 앞의 질문에 이미 답했다면 같은 내용을 다시 적거나 별도 권한표·정보 목록을 만들 필요는 없다. 해당하지 않는 상태나 예외를 억지로 추가하지 않는다.

직원을 직접 등록할지처럼 **사용자가 할 수 있는 일을 바꾸는 선택**은 PRD에서 정한다. 어느 테이블·API에서 정보를 가져올지는 상세 설계에서 정한다. 결과를 확인할 수 있게 적는 방법은 ⑤를 따른다.

#### 핵심 사용 흐름

PRD의 핵심 사용 흐름은 이번 범위의 일이 **무엇에서 무엇으로 이어져야 하는가**만 보여준다. 각 단계를 어떻게 수행하는지는 Use Case와 UX가 정한다. 같은 흐름의 원문은 PRD 한 곳에 두고, Use Case 목록과 UX 문서의 전체 윤곽은 이를 가리킨 뒤 각자의 상세를 덧붙인다.

| 넣는 것 | 넣지 않는 것 |
|---|---|
| 역할별 목적 → 핵심 행동 → 결과 | 화면 이름·화면 수·이동 경로 |
| 역할 간 인계 지점과 넘기는 내용 | 클릭·입력 단위의 조작, 안내 문구 |
| 결과에 영향을 주는 병렬 경로(외부 서비스 등) | 대체·예외 흐름의 분기, 상태별 반응 |
| 순서·포함 여부가 미결인 단계의 미결 표시 | 미결 단계의 임의 확정 |
| 각 단계의 기능 설명·Use Case 위치 | 기능 설명에 적은 규칙의 복제 |

여러 사용자의 일은 역할별로 줄을 나누고 인계로 잇는다. 모든 일을 하나의 긴 흐름으로 합치거나 제품의 모든 행동을 흐름에 넣지 않는다. 이번 범위에 있는데 흐름에 나타나지 않는 일이 있다면 누락인지, 따로 일어나는 일인지 확인한다. 흐름은 화면 순서를 확정하지 않으며, 순서가 업무 결과를 바꿀 때만 그 순서를 제품 결정으로 적는다. 문장·표·간단한 흐름도 중 이해하기 쉬운 형식을 고른다.

다음은 작성 방식의 가상 예시이며 헤어샵 예약 앱의 확정 요구가 아니다.

```text
고객   매장 진입 → 방문 시간 예약 → 예약 결과 확인
         ↓ 인계: 예약 내용
매장   예약 현황 확인 → 예약된 시간에 고객 맞이
미결: 확정된 예약의 고객 변경 허용 여부 — 예약 변경 UX 설계 전 결정
```

### ④ 제품 전체의 사용 환경과 운영 조건

기존 명칭은 ‘공통 사용·운영 요구’다. 기기와 장소·접속의 **기본 사용 조건**은 적고, 나머지는 해당할 때만 제품 결정에 필요한 만큼 적는다.

| 항목 | 적을 내용 | 작성 여부 |
|---|---|---|
| 사용할 기기 | 주로 어떤 기기에서 사용하는지 적는다. 특별한 제약이 없다는 답도 가능하다. | 필수 |
| 장소·접속 환경 | 어디서 쓰며 인터넷 연결이 필요한지 등 기본 사용 조건을 적는다. 특별한 장소 제한이 없으면 그렇게 적는다. | 필수 |
| 제품 전체의 데이터 접근 제한 | 사용자·조직에 따라 접근이 제한되면 적는다. ③에 이미 적은 범위를 반복하지 않는다. | 해당 시 필수 |
| 데이터 보관 | 보관 기간이나 이력 유지가 업무 결과에 영향을 줄 때 적는다. | 해당 시 필수 |
| 데이터 삭제 | 삭제 가능 여부와 삭제 후 결과가 제품 결정일 때 적는다. | 해당 시 필수 |
| 데이터 복구 | 저장한 업무 데이터의 복구 필요성이 제품 요구를 바꿀 때 적는다. 복구 기술은 상세 설계에서 정한다. | 해당 시 필수 |
| 감당할 지연·손실 | 허용 수준이 제품 동작이나 설계 선택에 영향을 줄 때 적는다. 근거 없는 수치는 만들지 않는다. | 해당 시 필수 |
| 문제 대응 주체 | 사용자에게 넘길 상대나 대체 절차가 업무 흐름에 영향을 줄 때 적는다. | 해당 시 필수 |
| 알려진 운영비·외부 시스템 제약 | 이미 정해졌고 이번 제품의 범위나 동작에 영향을 주면 적는다. | 해당 시 필수 |

**확인할 것:** 다음 상황의 영향을 살피고, 제품 요구를 바꿀 만큼 중요하면 필요한 조건을 적는다.

- 서비스가 중단되면 업무가 멈추는가? 다른 방법으로 처리해야 하는가?
- 데이터가 사라지면 다시 입력할 수 있는가? 업무 결과가 훼손되는가?

비개발자는 업무 상황과 영향을 설명하고, AI는 기술적 대안·비용·제약을 설명한다. ‘안전하게·빠르게’만 적거나 기술 이름부터 고르지 않는다. 모르는 조건은 미결로 남긴다. 제품 공통 조건은 한 번 쓰고 특정 기능만 다른 조건은 해당 기능에 적는다. 백업 도구의 선택과 실제 복구 가능성의 검증도 구분한다.

### ⑤ 충족 기준(Acceptance Criteria)과 미결 사항

| 항목 | 적을 내용 | 작성 여부 |
|---|---|---|
| 확인할 행동·결과 | 이번 범위의 요구가 이루어졌는지 판단할 수 있게 적는다. ③의 기능 설명만으로 충분하면 다시 쓰지 않는다. | 필수 |
| 허용·금지 확인 기준 | 금지하거나 제한하는 행동이 있다면 어떤 조건에서 막혀야 하고 결과가 무엇인지 확인 가능하게 적는다. 모든 기능에 금지 사례를 만들지 않는다. | 해당 시 필수 |
| 미결 질문 | 아직 못 정한 제품 결정이 범위·행동·결과에 영향을 줄 때 기록한다. 미결은 숨기거나 임의로 확정할 대상이 아니다. | 해당 시 필수 |
| 확인할 가정 | 확인되지 않은 전제에 기대어 제품을 결정했고, 전제가 틀리면 요구가 달라질 때 표시한다. 모든 생각을 가설 목록으로 만들지 않는다. | 해당 시 필수 |
| 결정 시점 | 미결 질문이나 중요한 가정이 있다면 어느 설계·구현 전에 확인할지 적는다. 날짜나 상세 검증 계획까지 PRD에 요구하지 않는다. | 해당 시 필수 |

충족 기준은 해당 기능 아래에 두어도 되며 같은 내용을 중복 작성하지 않는다. ‘정상 동작’처럼 판정할 수 없는 표현은 행동과 결과로 바꾼다. PRD에는 확인할 제품 결과를 적고, 세부 테스트 코드와 실행 절차는 후속 검증 계획에서 구체화한다.

### 해당하는 제품에서 더 확인할 내용

| 상황 | 구체화할 내용 |
|---|---|
| 기존 데이터를 가져와야 한다 | 가져오기 제공 여부와 중복·실패가 업무 결과를 바꾸는지, 이전 준비와 업무 중단 조건 |
| 외부 서비스와 연결해야 업무가 끝난다 | 필요한 연결과 실패 시 업무 결과, 알려진 외부 제약 |
| 결제나 민감한 정보를 다룬다 | 필요한 행동·접근 범위·데이터 보호, 적용 여부를 확인할 외부 의무 |
| 여러 사람이 같은 기록을 변경하거나 이력이 중요하다 | 동시 변경 시 결과, 수정 권한, 남겨야 할 이력 |

해당 여부부터 확인한다. 모든 제품에 이 기능들을 추가하지 않는다. 행동과 결과는 ③에, 제품 공통 조건은 ④에, 미결 질문과 시점은 ⑤ 또는 해당 요구 옆에 둔다.

## 3. 직접 따라 하는 작성·검토 순서

### 먼저 제품 전체를 개괄한다

아이디어와 기존 자료로 제품의 방향, 이번 범위, 사용자별 목적과 알려진 조건을 적는다. 처음부터 모든 기능을 같은 깊이로 작성하지 않는다. 합의된 내용·AI의 제안·미결 사항을 구분한다.

개괄에서 사용자별 목적이 드러나면 [핵심 사용 흐름](#핵심-사용-흐름)의 초안을 적는다. 처음에는 거칠어도 되며, 아래 검토로 기능과 규칙을 구체화하면서 단계·인계·미결을 함께 고친다.

그다음 대표적인 사용 상황 하나를 출발점으로 아래 세 가지를 살핀다. 이는 작성 순서이지 제품의 모든 일이 하나의 흐름으로 이어진다는 뜻이 아니다. 사용자가 제품에서 하려는 일은 코딩 작업을 나눈 구현 Task와도 구분한다.

### 1. User Story로 사용 맥락을 살핀다

사용자 입장에서 어떤 상황에서 무엇을 이루려는지 살핀다. 행동의 연결이 제품 결과를 바꾼다면 그 부분만 덧붙인다.

예: **고객은 방문 시간을 예약하려 하고, 매장은 예약 내역을 확인하려 한다.**

헤어샵 예약은 범용 기준을 이해하기 위한 예시다. 예약 기능·정책을 확정하거나 별도 제품의 PRD를 작성한 것은 아니다.

### 2. 중심 데이터에 관련 행동과 규칙을 모은다

‘예약’처럼 제품에서 다루는 정보를 중심으로 관련 행동을 묶는다. 여기서 데이터는 DB 테이블이 아니다.

| 중심 데이터 | 관련 행동 예시 | 함께 확인할 규칙 예시 |
|---|---|---|
| 예약 | 가능한 시간 조회·예약·변경·취소 등의 제공 여부를 검토 | 누가 할 수 있는가? 어떤 조건에서 가능한가? 처리 후 무엇이 남는가? |

예: **같은 시간에 여러 예약을 받을 수 있는가?** 제공할 행동과 결과에 영향을 주는 제품 결정이다.

‘예약 관리’라는 이름만으로 끝내지 않고, 허용 조건이나 업무 결과가 달라지는 행동을 구분한다. 모든 클릭을 기능으로 나누거나 행동마다 별도 문서를 만들 필요는 없다.

### 3. 주요 행동에 필요한 정보가 준비되는지 점검한다

주요 업무 흐름에서 필요한 정보가 없어 행동을 시작하거나 끝낼 수 없는 지점이 있는지 살핀다. 모든 정보의 출처를 분류하거나 준비 방법의 100% 목록을 만들지는 않는다.

예: 고객이 방문 시간을 고르려면 예약 가능한 시간 정보가 필요하다. 매장이 이 제품에서 정할지, 기존 일정에서 가져올지 확인한다. 어느 쪽인지 정하지 못했다면 미결로 남기고 관련 설계 전에 결정한다.

이 확인이 직원 관리 전체나 외부 일정 연동을 자동으로 추가하라는 뜻은 아니다. 매장이 예약 가능한 시간을 직접 정하는 것으로 충분할 수도 있다. 어느 테이블·API를 사용할지는 상세 설계에서 정한다.

### 사례로 검토하고 다른 흐름으로 넓힌다

정상 처리를 확인하고, 해당 업무에 중요한 금지·취소·반려·실패 상황이 있다면 가능한 행동과 결과를 확인한다. 필요한 경우 간단한 화면 초안으로 이해하고, 새로 발견한 제품 요구를 PRD에 반영한다.

대표적인 사용 상황부터 상세히 논의하되, 필요한 주변 행동을 확인하고 이번 범위의 다른 사용자·기능으로 넓힌다. 하나에서 시작하는 것은 작성 순서이며 PRD에 그 사례만 남긴다는 뜻이 아니다. 모든 화면 경로나 경우의 수를 빠짐없이 나열하라는 뜻도 아니다.

다른 사용자·기능으로 넓히면서 핵심 사용 흐름에 빠진 역할·단계·인계가 없는지, 흐름의 각 단계가 기능 규칙과 맞는지 확인한다.

사용 환경과 운영 조건도 ②~⑤의 확인 항목과 함께 점검한다. 기능 규칙만 검토하고 끝내지 않는다.

## 4. 어디까지 PRD에서 정하는가

**사용자가 할 수 있어야 하는 일과 그 결과는 PRD와 연결된 Use Case에서 정한다. Phase II의 Design에서 화면으로 검토하고, 2차 UX에서 조작·상태·흐름을 구체화한다.**

**업무상 서로 다른 제품이 될 수 있는 선택은 PRD에서 결정한다. 같은 제품 동작을 만드는 여러 방법은 설계에서 결정한다.**

### 같은 사례를 관점별로 구분하기

아래는 판단할 내용의 예시이며, 헤어샵 예약 앱의 확정 요구가 아니다.

| 관점 | 헤어샵 예약 예시 |
|---|---|
| User Story | 고객은 방문 시간을 예약하려 하고, 매장은 예약 현황을 확인하려 한다. |
| 핵심 사용 흐름 | 고객: 매장 진입 → 방문 시간 예약 → 결과 확인. 인계: 예약 내용 → 매장: 예약 현황 확인 |
| 기능 규칙 | 예약 확정 시점과 같은 시간의 중복 예약 허용 여부 등을 결정한다. |
| 사용 환경 | 고객과 매장이 사용할 기기·장소·접속 환경을 정한다. |
| UX | 예약 가능한 시간을 목록·달력 중 어떻게 보여줄지 설계한다. |
| 운영 조건 | 예약 기능이 중단됐을 때 대체 접수가 필요한지 검토한다. |

UX는 정보 제공·조작·실수 예방·실패 후 진행 방식을 구체화한다. 버튼 위치만을 뜻하지 않는다. 업무상 필요한 안내·확인이나 고정된 UX 제약은 PRD에 들어갈 수 있다. 예를 들어 다른 사람의 작업에 영향을 주는 행동 전에 영향을 알리고 확인받아야 한다는 요구는 PRD에 적고, 구체적인 문구와 화면 구성은 UX에서 정할 수 있다.

Design·UX 검토에서 새로운 업무 행동이나 규칙이 필요해지면 PRD와 해당 Use Case를 맞춘다. API 경로·DB 테이블·코드 구조와 모든 시각적 세부사항을 PRD에서 정하지 않는다. 이미 정해진 외부 제약은 기록한다.

### 공통 규칙과 기능별 예외

같은 규칙은 한 번 적고 적용 범위를 밝힌다. 해당 기능에는 다른 조건만 추가한다. 이 작성 방식은 ④의 운영 조건에만 적용되는 것이 아니다.

다음은 작성 방식의 가상 예시이며 헤어샵 예약 앱의 확정 정책이 아니다.

> **공통 규칙:** 매장 직원은 소속 매장의 예약을 조회할 수 있다.
>
> **예외:** 고객 연락처는 예약을 처리하는 직원만 조회할 수 있다.

각 화면에 같은 권한을 반복하지 않는다. 규칙과 예외가 겹치는 사례로 실제 허용·금지 결과를 확인한다.

### 행동을 빠뜨리지 않되 모두 만들지는 않기

조회·생성·수정·삭제를 뜻하는 CRUD는 누락 점검 도구다. 모든 데이터에 네 행동을 전부 제공하라는 뜻이 아니다. 업무 상황에 필요한 행동인지 검토하고 제공·미제공·이번 범위 제외·미결을 구분한다.

삭제는 제공 여부부터 결정한다. 제공한다면 가능한 사람·시점·기록에 남는 결과를 정한다. 삭제를 제공하지 않는 것도 제품 결정이다. 복사 같은 행동은 반복 작성의 불편을 해결할 필요가 있는지 확인하며, 떠올릴 수 있다는 이유만으로 추가하지 않는다.

핵심 기능인지 여부는 PRD 포함 기준이 아니다. 실제 사용에 필요한 행동이면 제품 요구다. 필요한 기능인지, 이번 범위에 넣을지, 언제 상세히 결정할지는 구분한다.

### 처음부터 정할 것과 미결로 남길 것

다음 설계에 필요한 중요한 역할·권한·업무 결과를 추측할 필요가 없도록 구체화한다. 아직 만들지 않을 기능의 모든 예외를 같은 깊이로 확정하지 않는다. 판단할 근거가 부족하면 질문과 결정 시점을 남긴다.

예: ‘확정된 예약의 시간을 고객이 변경할 수 있는가?’를 모른다면 미결로 적고, 예약 변경 UX를 설계하기 전에 결정한다. UX 탐색으로 답을 찾을 질문은 탐색 중에 해결할 수 있지만, 그 결정에 의존하는 구현에 그대로 넘기지는 않는다.

위 기준은 범용 PRD의 최소 수준이다. 개별 제품에서 필요한 규칙과 실제 기능별 세부사항은 해당 업무에 맞춰 정하며, 2차 Spec의 상세 작성법은 별도로 논의한다.

## 5. 보완 수단 — AI 검토와 인터뷰

직접 작성한 내용도 완벽하지 않을 수 있다. AI를 이용해 빠진 정보·충돌·확인하지 않은 가정을 찾는다. AI의 질문에 답하는 것만을 기본 작성 절차로 삼지는 않는다. 필요한 경우 초안 정리도 도움받을 수 있으나 검토 전 제안으로 취급한다.

### 누락을 점검할 때

**[실행 프롬프트] PRD 누락·충돌 검토**

- **목적·받을 결과:** 현재 PRD에서 빠진 내용과 충돌을 찾아 검토 결과를 받는다. 파일은 수정하지 않는다.
- **사용·복사 범위:** 이 가이드와 현재 PRD를 제공하고, 아래 코드 블록의 대괄호를 채워 복사한다.

```text
첨부한 PRD 가이드에 따라 현재 PRD를 검토해줘.
- 사용자별 목적과 사용 맥락(User Story) → 중심 데이터별 행동과 규칙을 따라 누락과 충돌을 찾아줘. 별도 User Story 목록이나 모든 경로를 요구하지 마. 필요한 정보가 준비될 수 있는지도 점검하되 모든 출처를 목록화하지 마.
- 핵심 사용 흐름이 있다면 각 단계가 이번 범위·기능 규칙과 연결되는지, 끊긴 인계나 흐름에 나타나지 않는 범위의 일이 있는지 확인해줘. 흐름이 없는 것 자체를 결함으로 보지 말고, 여러 역할이 맞물려 연결이 보이지 않을 때만 제안해줘.
- 사용 환경과 운영 조건도 확인해줘. 해당 없는 기능을 추가하지 마.
- 합의된 내용·네 제안·미결 사항을 구분하고 기존 답변은 재사용해줘.
- 문제의 구체적인 사례와 다음 설계에 미치는 영향을 설명해줘.
- 문서는 수정하지 말고 검토 결과를 먼저 보여줘.

현재 PRD: [내용 또는 파일 제공]
```

### 막힌 결정을 인터뷰로 보완할 때

**[실행 프롬프트] PRD 미결 사항 인터뷰**

- **목적·받을 결과:** AI의 질문에 답하며 막힌 제품 결정을 정리한다. 문서 반영은 별도 요청한다.
- **사용·복사 범위:** 현재 PRD와 미결 사항을 제공하고 아래 코드 블록을 복사한다.

```text
현재 PRD의 미결 사항을 함께 결정할 수 있도록 도와줘.
- 다음 설계에 영향을 주는 질문부터 한 번에 1~3개만 묻고 내 답을 기다려줘.
- 먼저 권장 기준과 이유를 설명한 뒤 구체적인 상황과 선택지를 제시해줘. 선택지 수정이나 다른 답, 보류도 허용해줘.
- 모르는 업무 정책·수치·기술 선택을 임의로 확정하지 마.
- 기능 규칙뿐 아니라 사용 환경·운영 조건의 빠진 결정도 확인해줘.
- 마지막에 결정·미결 사항과 판단 시점을 정리해줘. 문서 반영은 내가 요청했을 때 해줘.
```

AI의 제안, 사람의 결정, 파일 저장은 서로 다르다. 설명을 듣고 이해한 것과 구현을 검증한 것도 구분한다.
