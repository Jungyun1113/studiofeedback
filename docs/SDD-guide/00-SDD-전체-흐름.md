# SDD 전체 흐름

비개발자 1~2명이 AI와 함께 실제 사용자가 데이터를 입력하고 업무에 사용할 제품을 만들기 위한 진행 가이드다. 사람이 제품 결정을 이해하고 정하며, AI는 정리·대안 설명·설계·구현·검증을 돕는다.

## 1. 읽는 순서와 문서 역할

| 문서 | 이 문서에서 확인할 것 |
|---|---|
| 전체 흐름 — 현재 문서 | 단계의 순서, 목적, 산출물과 연결, 구현·검증의 전체 흐름 |
| [PRD 가이드](./01-1-PRD-가이드.md) | 1차 Phase I: 제품 요구의 내용과 작성·검토 방법 |
| [Use Case 가이드](./01-2-Use-Case-가이드.md) | 1차 Phase II: 사용자 목표별 흐름·조건·결과의 작성법과 예시 |
| [Design 가이드](./01-3-Design-가이드.md) | 1차 Phase II: 화면 검토 범위·완료 수준·남길 결과 |
| [2차 Spec 가이드](./02-2차-Spec-가이드.md) | 1차 작업물을 바탕으로 FE·BE 아키텍처, API Spec, DB Model과 UX를 구체화하는 방법 |
| [구현·검증 루프 가이드](./03-구현-검증-루프-가이드.md) | 기능별 Plan–Implement–Validate의 절차, 판단 경계와 완료 증거 |
| [실행 프롬프트](./04-실행-프롬프트.md) | 로드맵·Plan·Implement·Validate·피드백 반영 지시 |
| [Context](./CONTEXT.md) | 방법론의 배경, 이전 경험, 참고 자료 해석과 논의 맥락 |

가이드 파일과 실제 프로젝트의 산출물은 구분한다. 예를 들어 2차 가이드가 하나라고 해서 실제 프로젝트의 UX·DB·API Spec을 반드시 한 파일로 합친다는 뜻은 아니다.

작성 항목의 필요성은 **작성 여부**로 표시하며, **필수 · 해당 시 필수 · 권장 · 선택**을 같은 뜻으로 사용한다. 각 구분의 뜻과 미결 처리 방법은 [PRD 가이드의 공통 설명](./01-1-PRD-가이드.md#2-prd에-담을-내용)을 따른다. 작성 방법과 검토 질문은 표 아래에 따로 설명한다. **완료 수준**은 화면이 어디까지 동작하는지, **상세 수준**은 내용을 얼마나 자세히 쓰는지를 뜻한다.

1차는 Phase I에서 PRD를 작성하고 Phase II에서 Use Case와 Design을 함께 검토한다. 2차는 이를 입력으로 FE·BE 아키텍처, API Spec, DB Model과 UX를 만든다. UX 외의 Spec 상세 작성법과 미결 사항은 해당 가이드에서 구분한다.

구현·검증 루프는 별도 가이드에 공통 실행 절차를 정리했다. 프로젝트별 기술 절차와 연결해 적용할 초판이며, 실제 프로젝트에서의 효과 검증은 남아 있다.

## 2. 전체 흐름

**1차 Phase I: PRD → 1차 Phase II: Use Case·Design → 2차: 기술 Spec·UX·구현 로드맵 → 단계별 구현·검증 → 통합·출시 검증**

화면이 있는 제품은 구현 구간에서 **FE 구현·검증·사람의 화면 검토를 반복 → 명세·API 계약 갱신 → BE 구현·검증 → 실제 연결 검증** 순서로 진행한다. 화면이 없는 작업은 호출·출력 등 해당 결과를 기준으로 같은 루프를 적용한다.

| 단계 | 할 일 | 산출물 | 다음 단계로 넘어갈 때 확인할 것 |
|---|---|---|---|
| 1차 Phase I | 무엇을 왜 만들고, 누가 어떤 일을 어떤 규칙으로 할지 정한다. | PRD와 미결 사항 | Use Case와 화면을 검토할 제품 방향·범위가 드러나는가? |
| 1차 Phase II | 사용자 목표를 Use Case로 풀고 Design을 보며 행동·결과를 검토한다. | 검토한 Use Case·Design, 보완한 PRD와 미결 사항 | 다음 설계에 필요한 제품 결정을 추측하지 않아도 되는가? [상세 기준](#2-2-1차에서-2차로-넘어가기-전-확인) |
| 2차 Spec | 1차 작업물에 맞춰 사용자 경험과 기술 구조를 구체화하고 서로 맞춰 본다. | FE 아키텍처, BE 아키텍처, API Spec, DB Model, UX. 필요한 기술스택 결정과 개발 로드맵 | 다음 구현 범위의 설계·검증 방법이 연결되고, 구현을 막는 결정이 해결됐는가? [상세 기준](./02-2차-Spec-가이드.md#5-구현으로-넘어가기-전-확인) |
| 단계별 구현·검증 | FE·BE·실제 연결 등 현재 범위에서 계획·구현·검증을 반복한다. | 해당 구간의 구현과 증거, 사람 검토 결과, 갱신한 명세와 연결 검증 대기 | 이번 구간의 필수 결과를 확인했는가? 후속 구간의 미검증을 구분했는가? |
| 통합·출시 검증 | 기능을 연결한 전체 업무와 실제 배포 환경·운영 준비를 검증한다. | 출시 판단 근거와 남은 문제 | 실제 사용자에게 제공할 조건을 충족했는가? |

1차 Phase II에서는 **Use Case ↔ Design**을 오가며 글과 화면으로 요구를 확인한다. 2차에서는 1차 결과와 이미 정한 기술 조건을 확인하고, 필요한 기술스택을 결정하며 **FE·BE 아키텍처·API Spec·DB Model ↔ UX → 정합성 검토 → 개발 로드맵**으로 연결한다. 나열한 문서가 엄격한 작성 순서는 아니며 서로 영향을 주는 결정은 함께 조정한다.

이 순서는 최초 설계를 고정하는 절차가 아니다. Phase I에서도 필요하면 화면 초안을 볼 수 있고, Phase II부터 Design을 정식 검토 대상으로 삼는다. 2차에서 새로운 제품 규칙이 필요해지면 PRD·Use Case로 돌아가 결정하고 화면도 맞춘다. 화면 검토는 실제 데이터 연동 검증과 구분한다. Design의 정적·클릭 가능·실제 연동 수준 중 어디까지를 1차 완료 기준으로 삼을지는 별도 결정 대상으로 남긴다.

### 2-1. 문서 간 역할과 연결

1차 결과는 사람이 검토한 PRD·Use Case·Design이다. 남은 미결 사항과 화면의 실제 동작 수준을 함께 명시한다. PRD를 먼저 완전히 고정한 뒤 다른 작업을 시작해야 한다는 뜻은 아니며, 글과 화면에서 발견한 내용을 오가며 보완한다.

PRD는 제품 방향·범위·공통 요구를 설명하고, Use Case는 목표별 상호작용과 결과를 풀어쓴다. 공통 규칙은 원문 한 곳에 두고 Use Case가 참조한다. 특정 흐름의 상세를 Use Case에 두었다면 PRD에는 요약·링크를 둔다. Design에서 제품 규칙을 새로 만들거나 서로 다른 문서에 같은 정책을 독립적으로 유지하지 않는다.

2차 UX는 이 화면과 Use Case를 입력으로 조작·상태별 반응·실수 예방·실패 후 진행을 정리하고 기술 Spec과 맞춘다. UX 문서가 2차에 있다는 이유로 1차에서 사용자 흐름을 생각하지 않는 것은 아니다. 2차에서 발견한 문제가 있으면 Design도 함께 수정한다.

| 내용 | 정리할 위치와 시점 |
|---|---|
| Mission에 해당하는 대상 사용자·제품이 해결하려는 문제 또는 사용자가 하려는 일, 필요에 따라 장기 방향·제품 경계 | PRD의 제품 방향에 포함 |
| 이번 범위·사용자 목적에 연결된 기능 규칙·사용 환경과 운영 조건·충족 기준·미결 사항 | PRD에서 전체 개괄 후 점차 구체화 |
| 이번 범위의 일이 역할 간에 어떻게 이어지는지 보여주는 핵심 사용 흐름 | 권장. 작성한다면 PRD ③ 첫머리에 원문을 두고, Use Case 목록과 2차 UX의 전체 윤곽이 참조 |
| 기술스택 | 요구와 비용·운영 조건을 근거로 선택할 때 별도 작성. 이미 정해진 외부 기술 제약은 PRD에 기록 |
| 개발 로드맵 | 범위와 설계를 통해 기능 간 의존 관계를 파악한 뒤 별도로 개발·출시 순서와 진행 상태를 관리 |

별도 Mission이나 Constitution 파일을 기본 산출물로 요구하지 않는다. 기술스택과 로드맵을 PRD 작성 전에 모두 완성할 필요도 없다. 참고 자료의 Constitution 해석은 [Context](./CONTEXT.md)에 둔다.

### 2-2. 1차에서 2차로 넘어가기 전 확인

- 이번 범위 전체를 개괄했고, 사용자별 목적과 제공할 행동·결과의 연결을 설명할 수 있는가? 핵심 사용 흐름을 두었다면 각 역할이 일을 시작하고 마칠 길과 인계가 보이는가?
- 그 설계를 위해 중요한 역할·권한·업무 정책을 새로 지어낼 필요가 없는가?
- 사용 환경과 운영 조건을 확인하고, 결정·미결·해당 없는 조건을 구분했는가?
- 어떤 행동과 화면·데이터 결과를 보면 요구를 충족했다고 판단할지 설명할 수 있는가?
- 남은 질문과 어느 설계·구현 전에 결정할지가 드러나 있는가?
- 이번 범위의 Use Case 목록과 필요한 상세 흐름·결과가 있고 PRD와 연결되는가?
- Design을 주요 Use Case로 검토했으며, 2차와 구현에서 참조할 화면·버전·수정 사항을 찾을 수 있는가?
- 화면으로 확인한 내용, 예시 데이터로만 동작하는 내용, 실제 연동·검증이 필요한 내용을 구분했는가?

이는 다음 설계를 시작할 준비다. 모든 기술 설계가 끝났거나 구현·출시가 가능하다는 의미가 아니다. 요구한 기능이 동작하는지와 사용자 문제가 실제로 줄었는지도 구분한다.

## 3. 코드 구현과 기능별 검증

2차에서 [함께 검토할 업무 흐름으로 나눈 로드맵](./02-2차-Spec-가이드.md#5-개발-순서와-다음-plan의-대상을-정한다)을 바탕으로 **Plan–Implement–Validate**를 반복한다. 단계 수를 고정하거나 화면 하나씩 기계적으로 분할하지 않는다. 전체 설계가 있어도 기능별 Plan은 필요하며, 이때 전체 설계를 매번 다시 만들지는 않는다. 단계별 입력·작업·판정과 실패 시 돌아갈 지점은 [구현·검증 루프 가이드](./03-구현-검증-루프-가이드.md)에서 다룬다.

| 단계 | 할 일 | 확인할 결과 |
|---|---|---|
| Plan | 현재 상태에서 범위·작업 순서·검증 기준을 구체화하고 이번에 가능해질 연결 검증을 회수한다. | 무엇을 구현하고 어떤 행동·결과로 확인할지 명확하다. |
| Implement | 해당 프로젝트에 필요한 구성요소를 연결해 구현한다. | 실제 검증을 수행할 수 있는 기능이 준비됐다. |
| Validate | 공통 기준과 원문 명세로 실제 화면·동작·출력, 해당 구간의 처리 결과와 기존 기능 영향을 확인한다. | 증거와 사람 검토를 근거로 해당 구간의 완료·실패·미검증을 판단하고 후속 연결 대기를 남긴다. |

Task는 구현을 나누는 수단이다. Task 완료나 코드 검사 통과만으로 사용자 기능의 완료를 선언하지 않는다. 브라우저·실제 호출·산출물 등 해당 환경에서 확인한 결과와 미검증 항목을 구분한다.

매 단계에서 발견한 문제와 사람의 피드백을 반영해 다음 범위·순서를 재검토한다. FE는 API Spec에 맞춘 목업으로 대표 흐름을 일찍 보여주고 정보 구성·배치·업무규칙을 검토한다. 제품 결정이 바뀌면 관련 명세와 API 계약을 맞춘 뒤 BE에 인계한다. FE에서의 조작 성공을 실제 권한·저장 결과로 보고하지 않는다.

미구현 연결은 원본 검증 기록에 재검토 조건과 예정 단계를 남기고, 로드맵·Plan은 내용을 알 수 있는 단계명·검증 항목 이름과 링크로 참조한다. 다음 Plan에서 다시 읽으며, 통과한 기록도 보존한다. 이미 검증할 수 있는 필수 연결을 후속 단계로 미루지 않는다. 사람의 판단을 기다리는 결정에 의존하는 작업과 BE 진입은 [다음 단계의 기준](./02-2차-Spec-가이드.md#다음-plan과-be로-넘기는-기준)을 따른다. [실행 프롬프트](./04-실행-프롬프트.md)는 FE용과 BE용을 구분한다. 각 프롬프트가 실제 프로젝트 Spec을 읽고 필요한 기준을 적용하며, BE 구현·검증에는 실제 FE 연결을 포함한다.

## 4. 통합 검증과 출시 준비

개별 기능이 연결된 전체 업무 흐름과 실제 배포 환경의 동작을 확인한다. 제품에 필요한 권한, 데이터 보호, 백업·복구, 장애 확인과 대응 등 운영 조건도 검증한다.

개별 기능 검증, 배포 환경 검증, 사용자 문제의 개선 여부는 서로 다른 확인이다. AI의 완료 보고나 문서 검토만으로 이를 대체하지 않는다. 구체적인 출시 검증 절차와 기준 작성법은 후속 논의 대상이다.

## 5. 변경과 문서 관리

- 같은 결정의 원문은 한 곳에 두고, 다른 문서는 필요한 맥락과 참조를 제공한다.
- 제품 방향·범위·업무 규칙은 PRD, 기술 선택과 근거는 기술스택, 구현 구조는 관련 Spec, 개발·출시 순서와 진행 상태는 로드맵에서 관리한다.
- 문서 분리는 적용 범위, 독립적으로 바뀌는지, 별도로 읽고 참조할 필요가 있는지로 판단한다. 막연한 제품 크기를 기준으로 삼지 않는다.
- 문서가 충돌하면 제품 의도·설계·계획 중 무엇을 바꿔야 하는지 판단하고 관련 내용을 맞춘다. 문서 이름만으로 우선순위를 정해 덮어쓰지 않는다.
- 기술 제약이나 일정 때문에 범위를 줄여야 한다면 제안과 영향을 드러내고, 결정 후 PRD와 로드맵 등 관련 문서를 갱신한다.
- 명세가 맞고 구현이 틀리면 구현을 수정한다. 구현 결과를 정당화하려고 요구나 충족 기준을 바꾸지 않는다.
- 요구사항, 확인할 기준, 실제 검증 결과를 구분한다. 확인하지 않은 것은 미검증으로 남긴다.
