# 2차 작업물 가이드 — 기획을 바탕으로 Spec 만들기

[전체 흐름](./00-SDD-전체-흐름.md)에서 2차에 해당한다. 1차 Phase I의 [PRD](./01-1-PRD-가이드.md)와 Phase II의 [Use Case](./01-2-Use-Case-가이드.md)·[Design](./01-3-Design-가이드.md)을 입력으로 **FE 아키텍처, BE 아키텍처, API Spec, DB Model, UX**를 만들어 코드 구현의 근거를 갖춘다.

현재 문서는 기존에 정리한 방향·산출물 역할·검토 기준을 모은 가이드다. UX 문서를 직접 작성하고 검토하는 방법은 4절에서 다룬다. 전체 설계와 기능별 Plan의 공통 경계는 [구현·검증 루프 가이드](./03-구현-검증-루프-가이드.md#4-1-공통-설계와-기능별-plan의-경계)에 정리했다. 다른 Spec의 상세 작성법과 프로젝트별 적용 예시는 후속 구체화 대상이다. UX 작성법을 정리했다는 이유로 2차 방법론 전체가 완성된 것으로 보지 않는다.

## 1. 시작할 때 준비할 것

검토한 PRD·Use Case·Design, 알려진 외부 제약, 1차의 미결 사항과 화면 검토 결과를 읽는다. Design의 정적·클릭 가능·실제 연동 수준을 확인한다. 제품 규칙을 각 Spec에서 독립적으로 다시 정의하지 않는다.

설계에 필요한 제품 결정이 비어 있으면 PRD·Use Case로 돌아가 결정한다. 기술 제약 때문에 요구나 화면을 바꿔야 한다면 대안과 영향을 설명하고 결정 후 관련 문서를 맞춘다.

## 2. 만들 작업물과 역할

아래는 정리할 내용의 구분이다. 모든 항목을 각각 별도 파일로 만들어야 한다는 뜻은 아니다. 파일 분리와 결정 관리의 공통 원칙은 [전체 흐름](./00-SDD-전체-흐름.md#5-변경과-문서-관리)을 따른다.

| 작업물 | 구체화할 내용 | 사람이 확인할 것 |
|---|---|---|
| UX Spec | 1차의 Use Case·Design을 근거로 화면 연결, 정보 제공·조작, 상태별 행동, 실수 예방과 실패 후 진행을 정리·보완 | 사용자가 필요한 정보를 보고 업무를 끝낼 수 있는가? |
| 기술스택 문서 | 기술 선택, 근거, 대안과 제약, 비용·운영 부담, 공통 기술 기준 | 제품 요구와 감당할 운영 조건에 맞는가? |
| FE 아키텍처 | 검토한 화면을 구현할 구조, 화면·상태·데이터 접근의 책임, 공통 구성요소와 기능 연결 | 화면 기준을 유지하며 실제 기능을 연결할 수 있는가? |
| BE 아키텍처 | 업무 처리·권한·외부 연동·저장의 책임, 공통 구조와 기능 연결 | Use Case의 규칙과 결과를 지원하며 빠진 책임이 없는가? |
| DB Model | 저장할 정보와 관계, 상태·이력 및 필요한 실제 테이블·컬럼·제약의 표현 | 필요한 정보가 보존되며 업무에 맞는가? 중복이나 불필요한 복잡성이 없는가? |
| API Spec | 사용자 행동에 연결되는 입력·처리 결과, 권한과 실패 조건 | PRD의 허용·금지와 데이터 결과를 지원하는가? |

Design은 1차 Phase II에서 만든 입력이며, 2차의 UX·기술 검토로 필요한 수정이 생기면 함께 갱신한다. DB Model은 여기서 저장 설계까지 포함하는 이름으로 사용한다. 업무 개념만 표현한 엔티티 관계도는 그 출발점이 될 수 있지만 실제 저장 설계의 완료를 뜻하지 않는다.

개발 로드맵은 Spec 자체와 역할이 다르다. 위 설계에서 범위와 의존 관계를 파악한 뒤, 구현에 들어가기 위한 별도 계획으로 개발·출시 순서와 진행 상태를 관리한다. PRD의 업무 규칙을 복제하지 않는다.

## 3. 진행 순서

### 1. Use Case·Design을 읽고 UX를 구체화한다

PRD·Use Case의 흐름과 행동을 1차 Design에서 수행하는 방법으로 구체화한다. 주요 흐름을 화면으로 따라가며 상태별 행동과 필요한 안내를 확인한다. UX 문서의 작성 순서와 상세 수준은 [4절](#4-ux-문서를-직접-작성하고-검토하는-방법)을 따른다.

1차에서 검토한 화면과 흐름을 출발점으로 삼고, 화면에 드러나지 않은 상태·실패 후 진행과 기술 연결을 보완한다. 새 업무 행동이나 규칙이 필요해지면 PRD·Use Case로 돌아가 결정한다. 목업에서 동작해 보이는 것과 실제 데이터 처리가 검증된 것은 구분한다. UX와 기술 설계는 서로 오가며 조정하므로 아래 번호가 문서별 일괄 확정 순서를 뜻하지 않는다.

### 2. 기술스택을 선택한다

제품 요구와 사용 환경·비용·운영 조건을 바탕으로 AI가 추천안·대안·선택 근거와 제약을 설명한다. 사람은 그 영향을 이해하고 판단한다.

기술 이름부터 고르지 않는다. 이미 정해진 계약·기존 시스템 제약을 반영하고, 불확실한 선택은 필요한 검증을 거쳐 결정한다. 기술 도입 자체를 데이터 보호나 복구의 검증으로 취급하지 않는다.

### 3. FE·BE 아키텍처·API Spec·DB Model을 함께 설계한다

제품 요구, Use Case, Design과 UX를 근거로 기술 구조를 도출하고 서로 맞춰 본다. DB를 항상 먼저 확정하는 순서로 고정하지 않는다. 목업 코드가 있다면 실제 구현에 재사용할 수 있는지 판단하고, 재사용 여부와 관계없이 검토한 화면·행동을 구현의 비교 기준으로 연결한다.

DB는 개념 관계도뿐 아니라 실제 테이블·컬럼·관계를 검토한다. API와 아키텍처는 사용자 행동·입력·결과에 연결해 설명한다. 비개발자가 코드를 읽기 어렵더라도 업무 적합성과 이력 표현, 중복·복잡성은 판단할 수 있게 제시한다.

### 4. 설계 전체의 정합성을 확인한다

사용자 흐름을 따라 **PRD·Use Case의 규칙과 결과 → Design·UX의 화면과 행동 → API의 처리 → DB에 남는 결과 → FE·BE의 책임**이 연결되는지 확인한다.

중요한 실패·취소·금지 상황에서도 같은 결과를 설명할 수 있어야 한다. 문서마다 다른 정책이 생겼거나 필요한 처리·정보가 빠졌다면 관련 결정을 정리한다. 요구가 잘못됐는지, 설계가 요구를 충분히 반영하지 못했는지 구분한다.

### 5. 개발 순서와 다음 Plan의 대상을 정한다

개발 로드맵은 **사전 검토된 Spec을 입력으로 받아, 각 단계가 끝날 때 사용자가 무엇을 보고 판단할 수 있는지**를 기준으로 나눈다. 화면 수·컴포넌트 수·작업량을 균등하게 배분하는 것이 목적은 아니다. 단계 수를 5개 등으로 미리 고정하지 않는다.

화면이 있는 제품의 기본 흐름은 **FE 구현·검증·사람의 화면 검토 → 영향받은 명세와 API Spec 수정 → BE 구현·검증 → 실제 연결 검증**이다. FE 구간에서도 여러 번의 Plan–Implement–Validate를 수행한다. 제품 전체 FE를 한 번에 완성한 후 처음 검토하는 방식으로 돌아가지 않는다. API·CLI 등 화면이 없는 프로젝트는 실제 호출·출력·산출물로 검토 단위를 정한다.

요구사항을 처음부터 다시 인터뷰하는 단계가 아니다. 문서를 실제 구현 순서로 연결하다가 범위·순서·의존 관계를 결정할 수 없게 만드는 누락·충돌이 발견될 때만 근거와 필요한 결정을 제시한다. 읽지 못한 자료를 추정하지 않고, 해당 부분만 보류하며 나머지 로드맵은 작성한다.

#### 로드맵을 나누는 순서

1. **검토할 업무와 판단을 찾는다.** Use Case별로 사용자가 달성할 일, 확인해야 할 정보, 중요한 업무규칙과 실패 조건을 적는다. 화면이 있으면 시작 화면부터 결과 확인까지 연결한다.
2. **함께 봐야 판단되는 부분을 묶는다.** 목록과 상세의 정보 배분, 입력과 결과, 승인과 상태 갱신 등은 한 검토 흐름으로 묶는다. Use Case 하나가 너무 크면 정상·대체 흐름으로 나눌 수 있고, 같은 판단에 필요한 여러 Use Case 일부를 함께 구현할 수도 있다.
3. **늦게 틀리면 많이 고칠 부분을 앞당긴다.** 핵심 정보 구조·배치·업무규칙을 대표 데이터로 일찍 검토한다. 성공 흐름을 바꾸는 권한·실패 조건은 같은 단계에 넣는다. 예외·접근성·기본 품질을 모두 마지막 단계로 미루지 않는다.
4. **선행 조건과 모의 처리 범위를 정한다.** FE는 API Spec의 요청·응답·오류 형태에 맞춘 목업으로 검토한다. 미구현 기능을 임의의 성공 응답으로 감추지 않는다. 실제 기술 가능성이 불확실해 화면·계약 자체를 바꿀 위험이 크면 좁은 조사·실험을 선행시키되, BE 전체 구현으로 범위를 넓히지 않는다.
5. **단계별 검토 질문과 검증 경계를 적는다.** 이번에 확인할 결과, 기존 부분과 연결해서 볼 내용, 아직 확인 못 하는 내용과 확인 가능해지는 조건을 남긴다. 연결 관리는 [검증 대기와 회수 규칙](./03-구현-검증-루프-가이드.md#6-4-미구현-연결을-남기고-회수하는-방법)을 따른다.
6. **분할을 검토하고 실행 중 조정한다.** 대부분의 핵심 질문이 후속 단계 없이는 답할 수 없다면 합치거나 순서를 바꾼다. 서로 무관한 판단이 너무 많아 검토하기 어렵다면 나눈다. 하나의 로드맵 단계 안에 여러 구현 Task나 작은 루프를 둘 수 있다.

공통 화면 틀·실행 환경 등 기반 작업은 필요한 만큼 선행할 수 있다. 그 자체의 실행 확인과 첫 사용 흐름을 적고, 사용자 기능 완성과 구분한다. 전체 화면 지도가 필요하면 Design을 활용하며 미구현 영역을 실제 동작처럼 꾸미지 않는다.

**DB 설계와 실제 구축 시점을 구분한다.** DB Model은 2차 Spec에서 마련하고 FE 피드백이 저장할 정보·관계·규칙을 바꾸면 갱신한다. 서버 DB의 실제 구현은 선택한 FE 검토 범위 종료 후, DB를 처음 사용하는 BE 단계에서 해당 API 구현의 선행 작업으로 배정한다. 그 단계에 필요한 개발·테스트 환경, 스키마·제약, 마이그레이션·테스트 데이터를 준비하고 이후 BE 단계에서 필요한 부분을 확장한다. 기존 DB는 재사용하며 전체 스키마를 한 번에 구현할 필요는 없다. FE의 화면 상태·목업 데이터 관리는 서버 DB 구축과 구분한다.

#### 로드맵에 남길 최소 정보

기존 로드맵 문서에 아래 내용을 담으면 된다. 단계별 별도 문서나 복잡한 추적 도구를 의무화하지 않는다.

| 항목 | 적을 내용 |
|---|---|
| 단계명·목표·작업 구간 | 내용을 알 수 있는 고유한 이름과 확인할 업무 결과. 화면 제품은 FE 구간과 BE·실제 연결 구간을 구분 |
| 범위와 근거 | 관련 Use Case·Design·UX·API 등 원문 위치, 포함·제외한 흐름 |
| 선행 조건 | 필요한 기존 기능·결정·환경, 실제 또는 목업 데이터 사용 여부 |
| 검토 질문·완료 기준 | 사람이 판단할 질문, AI가 실행할 대표 시나리오와 기대 결과 |
| 연결 검증 | 검증 기록의 항목 이름·링크. 원본의 선행 대상·재검토 조건을 참조하고 예상 회수 단계를 연결 |
| 상태 | 예정 / 구현 중 / 검증 대기·진행 / 사람 리뷰 대기 / 해당 범위 완료. 실패·미검증은 검증 기록에 연결하고, 상태를 확인할 근거가 없으면 미확인으로 표시 |
| 다음 대상 | 다음에 다룰 단계명과 진행에 필요한 선행 조건. 진행 상태와 별도로 표시 |

별도 코드형 ID는 기본으로 만들지 않는다. 단계와 검증 항목에 내용이 드러나는 고유한 이름을 붙이고 원문 링크로 연결한다. 기존 식별자가 있으면 유지해도 되며, 순서를 위한 목록 번호를 관리 ID처럼 사용하지 않는다. 단계의 순서가 바뀌어도 이름과 참조는 유지하고, 이름을 바꾸면 관련 참조도 함께 갱신한다. 단계가 없어지면 연결 검증을 다른 단계에 이관하거나, 범위 제외 결정과 이유를 남긴다. 미래 단계의 책임자가 사라진 대기 항목을 방치하지 않는다.

#### 로드맵을 읽어 같은 프롬프트를 반복한다

FE·BE 각각의 Plan·Implement·Validate 프롬프트를 단계마다 재사용한다. 로드맵 단계는 사람이 함께 검토할 결과의 단위이며, 그 안의 세부 구현 Task는 해당 Plan에서 나눈다. 매번 최신 로드맵·관련 Spec·Plan·검증 기록을 제공하고, 지정한 단계 또는 로드맵의 다음 대상을 현재 구현·선행 조건과 대조한다. 기록만으로 완료를 추정하거나 다음 단계까지 자동으로 구현하지 않는다.

예를 들어 ‘신청 목록·상세 검토’는 해당 범위 완료, ‘신청 승인·반려’는 예정이면서 다음 대상, ‘처리 이력·알림 확인’은 예정으로 표시할 수 있다. 승인·반려를 추가할 때는 목록·상세의 상태 갱신과 기존 동작도 검증한다. 이전 단계에서 확인할 수 없었던 연결이 가능해졌다면 그 단계에서 회수한다.

로드맵에는 진행 상태·다음 대상·검증 기록 링크를 두고, 실제 결과·증거·실패·미검증·연결 대기는 검증 기록 원본에서 관리한다. 구현을 마치면 검증 대기, 필수 검증을 통과해도 필요한 사람 리뷰가 남으면 사람 리뷰 대기다. 해당 범위의 완료 조건이 충족됐을 때만 완료로 갱신한다. 변경 영향을 받은 이전 완료 단계는 재검증·필요한 사람 리뷰 상태를 다시 표시하며 과거 증거는 보존한다. 저장 위치가 없어 답변으로 받은 결과도 다음 요청의 입력으로 이어 준다.

최초 단계라도 기존 프로젝트 코드가 있으면 관련 영향을 검토한다. 기존 구현이 전혀 없으면 이번 범위 자체를 확인하고 후속 연결 대기를 남긴다. 이후에는 새 구현·새 연결·영향받는 기존 동작을 단계마다 확인하고, 선택한 FE 범위 종료 전에는 여러 단계를 관통하는 주요 업무 흐름과 남은 대기를 점검한다. 이전 구현 전체를 매번 다시 검사할 의무는 없으며 공통 CSS·상태·계약 등 변경 영향에 따라 범위를 정한다.

#### FE 로드맵을 5단계로 나눈 예

신청 관리 제품이라는 설명용 가정이다. 5단계 모두 FE 구간이며 BE·실제 연결·출시 완료를 의미하지 않는다.

| 단계 | 함께 구현할 범위 | 화면을 보며 판단할 질문 |
|---|---|---|
| 신청 목록·상세 검토 | 목록 → 상세 → 목록 복귀, 대표 데이터, 정보·행동이 달라지는 주요 역할과 기본 상태 | 역할에 맞는 대상을 고르고 상세에서 판단하는 데 필요한 정보가 있는가? 정보의 배분·배치가 적절한가? |
| 신청 승인·반려 | 승인·반려 → 결과 표시 → 목록·상세 상태 갱신, 주요 권한·처리 불가 조건 | 판단에서 처리까지 자연스러운가? 허용·금지와 결과가 분명한가? |
| 다수 신청에서 처리 대상 찾기 | 다수 신청의 검색·필터·정렬 → 상세 확인 → 목록 복귀 | 많은 신청 중 처리할 대상을 찾고, 선택 조건을 유지하며 검토할 수 있는가? |
| 처리 이력·알림 확인 | 처리 이력·알림에서 관련 신청으로 이동 | 처리 결과를 추적하고 원래 업무로 돌아갈 수 있는가? |
| FE 구간 종료 검증 | 새 기능 구현 단계가 아니라, 구현된 경로를 연결한 업무 시나리오와 남은 검증을 확인 | 개별 화면 검사로 드러나지 않은 누락·중복·연결 문제가 있는가? FE 범위에서 확인 가능한 필수 검증이 끝났는가? |

이력이 승인 판단에 필수라면 ‘처리 이력·알림 확인’의 해당 부분을 ‘신청 승인·반려’로 앞당긴다. 검색·필터가 첫 검토부터 필수라면 ‘다수 신청에서 처리 대상 찾기’의 해당 부분을 ‘신청 목록·상세 검토’에 포함하고 별도 단계가 필요한지 다시 판단한다. 각 단계는 이미 필요한 역할·빈 상태·오류·접근성 등을 검사한다. ‘FE 구간 종료 검증’은 이전의 필수 미검증을 몰아서 처리하는 단계가 아니다.

#### 다음 Plan과 BE로 넘기는 기준

매 단계의 화면 검토에서 발견한 구현 결함은 수정하고, 제품 결정이 달라지면 PRD·Use Case 및 영향받은 Design·UX·API·DB·아키텍처를 맞춘다. 화면만 수정하고 API 계약은 이전 상태로 두지 않는다. 영향받은 기존 검증은 다시 수행한다.

**다음 단계는 사람의 판단을 기다리는 결정에 의존하는지 확인한다.** 예를 들어 목록의 정보 배분을 검토 중이라면 그 배분을 전제로 하는 후속 화면 구현은 기다린다. 이미 확정된 규칙의 테스트처럼 그 결정과 무관한 작업은 진행할 수 있다. 여러 단계를 한 번에 요청받았다는 이유로 필요한 사람 검토를 건너뛰지 않는다. 사람이 명시적으로 위임한 검토 범위는 그 기준을 적용하되 사람의 실제 검수로 기록하지 않는다.

**BE 진입 전에는 다음을 한 번에 확인한다.** 현재 선택한 FE 검토 범위가 끝나기 전에 기능마다 BE를 자동으로 붙이지 않는다. 다른 범위를 병행하려면 그 범위와 경계를 명시적으로 정한다.

- 대상 FE 흐름의 필수 AI 검증과 사람의 화면 검토 또는 명시적으로 위임된 수용 절차가 끝났고, 검토한 범위·버전과 이후 변경 영향을 확인할 수 있다.
- 화면 피드백을 반영한 업무규칙·설계·API 계약이 현재 FE 목업의 요청·응답·오류와 일치한다.
- 이번 BE 결과를 바꿀 수 있는 알려진 미결·후속 요구와 의존 관계를 확인했고, 구현에 필요한 결정은 해결됐다. 해결되지 않은 부분은 의존 범위와 함께 대기시킨다.
- FE에서 증명하지 못한 실제 권한·저장·외부 연동 등의 검증이 원본 기록에 남아 있고, BE 또는 실제 연결 구간의 실행 조건과 예정 단계가 연결돼 있다.

이 기준은 미래 변경이 없다는 보장이 아니다. 이후 결정이 바뀌면 영향받는 Spec·구현·검증을 갱신한다. 미결 부분을 대기시키는 것은 제품 범위를 임의로 삭제하거나 기능 전체를 완료로 처리하는 일이 아니다.

모든 기능의 세부 Task를 로드맵에서 한꺼번에 예측하지 않는다. 다음 범위의 구현 순서·검증 사례는 Plan에서 현재 상태에 맞춰 구체화한다. BE·실제 연결 로드맵도 같은 방식으로 작성하되 실제 권한·저장·오류·호환성 등 해당 결과를 검증 기준으로 삼는다.

복사해 사용할 [로드맵 작성 프롬프트](./04-실행-프롬프트.md#2-구현-로드맵-작성)와 [구현·검증 루프](./03-구현-검증-루프-가이드.md)를 연결한다. 여러 기능이나 외부 사용자가 의존하는 결정은 관련 Spec에 둔다.

## 4. UX 문서를 직접 작성하고 검토하는 방법

이 절은 비개발자 1~2명이 검토한 PRD·Use Case·Design을 바탕으로 UX를 직접 작성하고 AI와 함께 점검할 때 따른다. **UX는 사용자가 제품에서 가능한 일을 화면에서 어떻게 이해하고 수행하며 결과를 알아보는지** 정한다. UX 문서가 별도 파일이어야 한다는 뜻은 아니며, 아래 항목도 고정 목차나 모든 화면에 대한 작성 의무가 아니다.

### 4-1. 작성 단위와 상세 수준

작성 단위는 화면 한 장이나 클릭 한 번이 아니라 **사용자 목적을 이루는 과정**이다. 목적, 시작 상황, 주요 행동, 결과가 함께 설명되면 한 흐름으로 다룰 수 있다. 여러 사람의 일이 이어지면 인계 지점을 밝히고 각자의 경험을 구분한다. 같은 안내·조작 방식이 여러 흐름에 쓰인다면 공통 원칙을 한 번 적고 필요한 차이만 해당 흐름에 적는다.

| 상세 수준 | 어디에 적용하는가 | 무엇을 남기는가 | 멈출 기준 |
|---|---|---|---|
| 전체 윤곽 | 이번 범위의 사용자 목적과 주요 행동 | PRD의 [핵심 사용 흐름](./01-1-PRD-가이드.md#핵심-사용-흐름)을 가리키고, 누가 어디서 일을 시작하고 어떤 핵심 행동을 거쳐 결과를 어디서 확인하는지 덧붙인다. PRD에 흐름이 없다면 역할 간 인계나 중요한 연결을 함께 표시 | PRD에 있는 일을 사용자가 시작하고 마칠 길이 보인다 |
| 필요한 흐름의 상세 | 다음 구현 범위와, 이해 오류·실수·실패의 영향이 큰 흐름 | 판단에 필요한 정보, 조작과 화면의 반응, 중요한 상태 차이, 실수 예방, 실패 후 진행, 완료 확인 | 사람이 글과 주요 목업을 따라가며 사용 가능 여부를 판단할 수 있다 |

먼저 전체 윤곽을 보고 상세화할 곳을 고른다. 다음 구현 범위 외에도 권한·상태에 따라 행동이 달라지거나, 되돌리기 어렵거나, 여러 사람의 인계가 있거나, 실패 후 무엇을 해야 할지 불분명한 곳은 일찍 상세화한다. 해당하지 않는 상태와 예외를 억지로 만들지 않는다. 아직 구현하지 않을 모든 경로를 같은 깊이로 쓰지 않고, 상세화가 필요한 시점과 이유를 남긴다.

### 4-2. PRD에서 UX 초안으로 옮기는 순서

1. **근거를 읽는다.** PRD·Use Case에서 이번 범위의 사용자 목적, 가능한 행동, 필요한 정보, 허용·금지 조건, 결과, 사용 환경과 미결 사항을 확인하고 Design의 화면·검토 결과를 함께 본다. 이미 정한 제품 규칙은 UX에서 다시 결정하거나 길게 복제하지 않고 원문 위치를 가리킨다.
2. **전체 윤곽을 적는다.** PRD에 핵심 사용 흐름이 있으면 그것을 출발점으로 가리키고 다시 쓰지 않는다. 각 단계를 어디서 시작하고 결과를 어디서 확인하는지 덧붙인다. 흐름이 없다면 사용자 목적별로 시작 → 주요 행동 → 결과 확인을 짧은 문장이나 간단한 흐름으로 연결한다. 윤곽을 적다가 흐름의 단계·인계·순서를 바꿔야 한다면 UX에서 고치지 않고 PRD를 갱신한다. 정보가 준비되지 않아 일을 시작할 수 없는 곳, 다른 사람에게 일이 넘어가는 곳을 살핀다. 화면 이름·화면 수·모든 이동 경로부터 정하지 않는다.
3. **자세히 쓸 곳을 고른다.** 다음 구현 범위와 사용자 판단이나 업무 결과에 영향이 큰 순간을 표시한다. 선택 이유를 적어, 나머지를 누락한 것과 의도적으로 뒤로 미룬 것을 구분한다.
4. **그 순간을 사용자의 관점에서 풀어 쓴다.** 사용자가 무엇을 알고 보아야 하는지, 무엇을 할 수 있는지, 조작 뒤 어떤 반응과 결과를 보는지, 막히면 어떻게 이어가는지 적는다. 아래 항목 중 해당하는 것만 채운다.
5. **Design Spec·목업과 맞춰 본다.** UX에 적은 정보·행동·상태가 주요 화면에 드러나는지 사람이 직접 따라간다. 배치나 표현을 바꾸어야 이해할 수 있다면 함께 조정한다. 목업에서 새 제품 규칙이 필요해지면 PRD의 미결로 돌린다.
6. **이번 범위로 넓혀 확인한다.** 상세히 쓴 흐름 하나로 끝내지 않고 전체 윤곽의 다른 사용자 목적과 주요 행동에도 시작·완료 경로가 있는지 확인한다. 바뀐 결정은 관련 문서와 맞춘다.

### 4-3. 상세 흐름에서 상황에 따라 확인할 항목

다음 표는 상세화하기로 한 흐름에서 작성과 누락 점검에 사용할 질문이다. **작성 여부**는 [PRD 가이드의 구분](./01-1-PRD-가이드.md#2-prd에-담을-내용)을 따른다. 아래 항목은 모두 **해당 시 필수**로, 해당 흐름에 필요한 상황이나 조건이 있으면 적는다. 해당하지 않는 상태나 행동을 새로 만들지 않는다.

| 항목 | 적을 내용 | 작성 여부 |
|---|---|---|
| 시작과 이동 | 어디서 시작하고 필요한 단계로 어떻게 이동하는지. 중단 후 다시 들어와야 한다면 어디서 이어지는지 | 해당 시 필수 |
| 판단에 필요한 정보 | 행동 전 알아야 할 정보와 현재 상태. 정보가 없거나 아직 준비되지 않았을 때의 다음 행동 | 해당 시 필수 |
| 입력과 조작 | 무엇을 선택·입력·확인하는지. PRD의 필수 입력과 허용 행동을 어떻게 이해하고 수행하는지, 잘못된 조작을 어떻게 예방하거나 바로잡는지 | 해당 시 필수 |
| 권한·상태 차이 | 권한·상태에 따라 달라지는 정보와 행동. 필요한 경우 할 수 없는 이유와 다음 방법 | 해당 시 필수 |
| 처리 중·성공 | 필요한 접수·진행·완료 표시. 결과를 확인할 위치와 다음 일을 시작하는 방법 | 해당 시 필수 |
| 실패·중단·되돌리기 | 중요한 실패·중단 때 처리된 것과 남은 것. 수정·재시도·돌아가기 등 제품에서 허용한 다음 행동 | 해당 시 필수 |
| 다른 사람에게 인계 | 다음 담당자가 일을 알아차리고 시작하는 방법. 인계 상태와 필요한 안내 | 해당 시 필수 |
| 사용 환경 | PRD에 정한 기기·장소·접속 조건에서 핵심 정보를 읽고 행동하는 방법. 특별한 제약이 없다면 불필요한 화면별 명세를 늘리지 않는다. | 해당 시 필수 |

**작성할 때:** 문장·표·간단한 흐름도 중 이해하기 쉬운 형식을 고른다. 각 행을 모든 흐름의 별도 문단으로 만들 필요는 없으며, 다른 곳에 분명한 내용은 반복하지 않는다. 필요한 내용의 답을 아직 모르면 미결로 남긴다. PRD에서 제공하지 않는 행동을 UX에 임의로 추가하지 않는다.

업무상 중요한 경고·확인·안내는 **언제, 무엇을 이해시키고, 어떤 선택을 돕는지** 적는다. 정확한 문구가 제품 요구나 사용자 판단에 중요할 때만 그 문구까지 정한다. 모든 오류 문구와 클릭·화면 전환을 열거하지 않는다. PRD에 없는 행동 허용 여부, 결과, 인계 규칙이 필요해지면 UX 문장으로 숨기지 말고 제품 결정으로 표시한다.

### 4-4. PRD·Design Spec·목업·기능별 Plan과의 경계

| 작업물 | 해당 내용의 기준 |
|---|---|
| PRD | 누가 무엇을 할 수 있는지, 조건·권한·업무 결과가 무엇인지 정한다. 이번 범위의 일이 역할 간에 어떻게 이어지는지 보여주는 핵심 사용 흐름의 원문도 둔다. 업무상 반드시 필요한 안내나 고정된 UX 제약도 여기서 요구할 수 있다 |
| Use Case | PRD의 방향·규칙에 연결해 목표별 시작·성공·대체 흐름과 결과를 설명한다. 제품 동작의 상세 근거다 |
| UX 문서 | 그 행동을 시작하고 이해하고 수행하며 결과를 알아보는 방법을 정한다. 필요한 정보·조작·상태별 반응·실패 후 진행을 설명한다 |
| Design Spec | 1차 Phase II에서 정보와 행동을 화면에 어떻게 구성·배치·표현할지 기준을 만든다. 2차 UX와 기술 설계에서 보완한 내용도 반영한다 |
| 주요 목업 | 대표적이고 판단이 어려운 순간을 실제 화면처럼 보며 따라가고 수정한다. 모든 화면의 완성본이나 실제 기능·데이터 처리의 증거는 아니다 |
| 기능별 Plan | 해당 구현 범위에 필요한 세부 명세와 구현·검증 방법을 확정한다. 앞선 UX에서 중요한 사용자 판단을 비워 둔 채 Plan에 넘기지 않는다 |

파일을 나누는 기준과 관계없이 같은 결정의 원문은 한 곳에 둔다. UX는 기술 구조, API 경로, DB 테이블을 정하는 문서가 아니며, 시각적 수치와 모든 문구를 미리 고정할 필요도 없다. 다만 화면 표현이 사용자의 판단이나 결과 이해를 바꾼다면 단순한 꾸밈으로 미루지 않는다.

### 4-5. 사람이 화면에서 검토하는 방법

1. PRD의 사용자 목적과 결과를 옆에 두고, UX 문장의 시작부터 완료까지 사용자의 입장에서 읽는다. 필요한 정보가 보이기 전에 행동을 요구하거나, 완료·실패 여부를 알 수 없는 곳을 표시한다.
2. 주요 목업에서 실제 사용할 기기 조건을 고려해 해당 흐름을 따라간다. 화면을 처음 보는 사람처럼 어디를 보고 무엇을 선택할지, 처리 뒤 어디에서 결과를 확인할지 말로 설명해 본다.
3. 해당하는 중요한 상태·권한 차이, 실수, 실패, 중단, 인계를 적용해 본다. 모든 경우의 수를 나열하는 대신 사용자 행동과 결과가 달라지는 경우를 우선한다.
4. 발견한 문제를 **제품 결정 부족 / UX 설명 부족 / 화면 표현 문제 / 구현 단계에서 확인할 문제**로 구분한다. 필요한 결정, 수정할 문서, 다시 확인할 방법을 짧게 남긴다. 사람이 실제로 확인한 것과 AI가 추정한 것을 섞지 않는다.

글이나 정적 목업 검토는 **이해 가능성과 설계의 연결**을 확인한다. 클릭 가능한 목업이라도 저장·권한·API·DB 동작이 증명된 것은 아니다. 실제 동작과 데이터 결과는 구현 후 Validate에서 별도로 확인한다.

### 4-6. AI를 보완 수단으로 쓰기

사람이 먼저 초안을 작성하고, AI에는 PRD·Use Case의 해당 내용·현재 UX·관련 목업이나 Design Spec·이미 정한 제약을 함께 제공해 검토를 요청한다. AI가 흐름을 대신 발명하거나 빠진 제품 정책을 확정하지 않도록 한다.

AI에게는 PRD의 행동·조건·결과가 UX에서 이어지는지, 사용자가 필요한 정보를 제때 보는지, 중요한 상태·실패·인계에서 막히는지, Design Spec·목업과 충돌하는지를 확인하게 한다. 지적할 때는 근거 위치, 사용자에게 생기는 문제, 수정할 문서, 제안과 미결 여부를 구분하게 한다. 중요한 문제부터 적고 모든 화면·경로 목록이나 불필요한 기능 추가를 요구하지 않게 한다.

AI의 문장 수정안은 **제안**이다. 사람은 업무 의도와 실제 화면을 보고 채택·수정·보류를 결정한다. 결정한 내용이 제품 행동이나 결과를 바꾼다면 PRD에서 먼저 정리한다. 문서 검토 결과를 사람의 목업 검수나 구현 검증의 대체물로 보지 않는다.

### 4-7. 다음 설계·구현으로 넘길 때

- 이번 범위의 사용자 목적과 주요 행동에 시작·완료 또는 인계의 연결이 보이는가?
- 다음 구현 범위와 중요 상황은 필요한 정보·조작·상태·결과·실패 후 진행이 사람이 판단할 수 있을 만큼 설명됐는가?
- 주요 목업에서 해당 흐름을 사람이 따라가고, 발견한 문제를 관련 문서에 반영하거나 미결로 남겼는가?
- 새 제품 규칙을 UX에서 임의로 정하지 않았으며, 중요한 미결의 결정 시점이 해당 설계·구현보다 앞서는가?
- 기능별 Plan에서 더 정할 세부사항과 지금 사용자 경험에 필요한 결정이 구분됐는가?

이 확인은 UX 설계를 다음 작업의 근거로 사용할 준비다. 구현 완료, 실제 데이터 처리 검증, 출시 가능을 뜻하지 않는다.

## 5. 구현으로 넘어가기 전 확인

기존 가이드에서 유지하는 확인 기준은 다음과 같다.

- 다음 구현 범위에서 PRD·UX·기술 설계의 중요한 누락·충돌이 해결됐는가?
- 주요 화면과 업무 흐름을 사람이 검토했는가?
- 구현에서 계속 참조할 Design·화면 버전과 UX가 연결되고, 예시 동작과 실제 연결할 기능을 구분했는가?
- 구현할 행동이 API·저장 결과·FE와 BE의 책임에 연결되는가?
- 기능별 Plan에서 구체화할 내용과 그 전에 결정해야 할 미결 사항이 구분됐는가?
- 이번 작업 구간에서 화면·동작·데이터 결과를 확인할 방법과 환경이 있는가? FE 목업으로 확인할 것과 실제 연결에서 확인할 것을 구분했는가?
- 다음 로드맵 단계가 함께 검토 가능한 단위이며, 연결 대기의 회수 조건이 있는가?

아직 만들지 않을 기능의 모든 세부사항을 확정할 필요는 없지만, 미결 결정에 의존하는 구현 전에 그 결정을 해결한다. 이 기준은 다음 구현 범위의 준비를 확인하는 것이며, 구현 완료나 출시 가능을 뜻하지 않는다.

## 6. 이후 구체화할 미결 사항

- UX 외의 Spec을 직접 작성할 때의 구체적인 순서와 상세 수준
- 전체 설계·기능별 Plan의 공통 경계를 실제 프로젝트의 기술 결정에 적용하고 검증한 예시
- UX 외의 Spec에서 누락·충돌을 확인할 실제 검토 방법
- 실제 프로젝트에서 문서를 나누고 연결하는 구체적인 예시

이 항목들을 별도 합의 없이 확정된 표준 템플릿이나 필수 문서 수로 바꾸지 않는다.
